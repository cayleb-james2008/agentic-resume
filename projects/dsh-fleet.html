at a glance

What the fleet is

The fleet is a prompt-to-fruition machine: a prompt goes in, and a finished artefact comes out that has been built, checked by someone other than its builder, and recorded with the evidence that it works. A request becomes an order with a done-when rubric, a size, a tier and a budget. Orders are claimed with a lease, checkpointed, and closed only against the rubric.

Work runs in model-independent lanes — lead, delegator, builder, checker and researcher — each with its own session and working directory. A lane is a slot: the model inside it can change without changing the shape of the work. Work arrives on a message bus, so nobody sits and watches a queue.

What is checked, and by whom

The lane that builds a thing cannot grade it. Grading runs in a separate session that receives the artefact and the rubric, not the builder's reasoning, and it can fail. Three rounds is the cap; after that the work is reported as it stands rather than argued over. Cost, holds and provider fallback are recorded per run, so a result can be traced to the engine that answered.

Both the maker-never-checker rule and the per-stage check scripts are in the repository this page describes. The page's claim is deliberately narrower than the old one: it describes the harness that the current tree documents, not a feature that the tree marks as missing.

Where the current tree stands

The current tree is the APEX build. Its behaviour survival map lists each earlier ruled behaviour against the new tree and marks it restored, partial or a named gap. One of those named gaps is the dynamic-swarm shape itself: the APEX rewrite deleted it, so this page no longer presents dynamic swarms as a current feature. What is present is the Omni engine: Pareto multi-objective evaluation plus the automated main-release commit path in package/src/omni.

The fleet is in active development. The code repository is private; this page is its public record.
